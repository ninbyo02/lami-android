LiteRT Qualcomm dispatch source trace
Date: 2026-05-21

Scope: source-only trace. No source modified, no build run, no inference or dry-run run.

Core finding:
`No usable Dispatch runtime found` is emitted by LiteRT's dispatch delegate after dispatch API initialization fails. It is not just a missing-library message. A dispatch `.so` can exist and export `LiteRtDispatchGetApi`, while still being unusable because the dispatch API cannot initialize QNN/HTP, fails version checks, fails SoC/device setup, or cannot later consume the model's embedded dispatch bytecode.

Exact fatal path:
- LiteRT/litert/runtime/dispatch/dispatch_delegate.cc:112-120
  `Initialize()` calls `InitializeDispatchApi()`. On failure it logs `Failed to initialize Dispatch API: ...` and sets `has_dispatch_runtime_ = false`.
- LiteRT/litert/runtime/dispatch/dispatch_delegate.cc:125-132
  `CreateDelegateKernelInterface()` checks `has_dispatch_runtime_`; false emits:
  `Failed to create a dispatch delegate kernel: No usable Dispatch runtime found`.

Why `LiteRtDispatchGetApi` is insufficient:
- It only proves the dispatch shim can return a `LiteRtDispatchApi` struct.
- It does not prove version compatibility, QNN library availability, QNN provider/API compatibility, HTP SoC/device creation, capability bits, or compiled model context-binary compatibility.
- The fatal observed here occurs when `has_dispatch_runtime_` is false, which is set after any `InitializeDispatchApi()` failure.

Required runtime/model conditions inferred from source:
- Compatible `libLiteRt.so`, LiteRT-LM JNI, and `libLiteRtDispatch_Qualcomm.so` dispatch API/C API versions.
- QNN libraries from the expected QAIRT generation:
  `libQnnSystem.so`, `libQnnHtp.so`, likely `libQnnHtpPrepare.so`, and SM8750/V79 stub/skel artifacts such as `libQnnHtpV79Stub.so` and `libQnnHtpV79Skel.so`.
- Android app namespace and `ADSP_LIBRARY_PATH` must make those QNN and V79 artifacts reachable.
- Device platform info must map to supported SM8750/V79. This tree maps SM8750 to V79/8 MB VTCM in:
  - LiteRT/litert/vendors/qualcomm/core/schema/soc_table.cc:42-44
  - LiteRT/litert/vendors/qualcomm/supported_soc.csv:4
- `.litertlm` must contain TFLite model sections with section metadata and dispatch custom ops whose options point to valid embedded QNN context binaries.
- The embedded QNN context binaries must be compiled for the target SoC/HTP arch and compatible QNN runtime generation.

Conditions that can collapse to `No usable Dispatch runtime found`:
- No dispatch runtime found in dispatch library dir.
- Wrong selected dispatch runtime among multiple candidates.
- Dispatch `.so` load failure or missing `LiteRtDispatchGetApi`.
- Dispatch API struct version mismatch.
- Qualcomm initialize failure before capabilities/device context.
- Missing/unloadable `libQnnSystem.so` or `libQnnHtp.so`.
- Missing/failing QNN provider symbols.
- QNN core/backend API major mismatch or too-old minor version.
- HTP platform info unsupported or no DSP arch mapping.
- HTP backend/device/perf-control setup failure.
- Missing basic dispatch capability or failed `LiteRtDispatchDeviceContextCreate`.

Bottom line:
The source strongly supports treating the observed failure as a generic late symptom of an earlier dispatch runtime initialization failure. With dispatch `.so` and `LiteRtDispatchGetApi` present, the likely remaining classes are QAIRT/QNN generation mismatch, Android QNN/V79 library path or namespace failure, unsupported/misdetected SM8750/V79 HTP setup, or compiled model/QNN context binary mismatch.

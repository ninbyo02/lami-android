# TTSの所有者一本化と停止確認

## 問題と変更

NPUの途中出力を文単位でQUEUE_ADDに送る経路と、完了後に全文をQUEUE_FLUSHで送るphase経路が別々に存在した。完了後に読み直し得るほか、TTSコールバックとstopが別スレッドでキューを操作していた。

ResponseSpeechSessionで回答ごとの消費位置・完了・停止世代を管理する。通常チャットの自動読み上げは共通キューへ送り、NPUも途中出力から読み上げ、完了時は未読末尾だけを送る。停止は当該回答の自動読み上げを失効させる。メモリ解放待ちの後にも世代を再確認し、手動再生も停止・次の操作後に古い準備処理から再開させない。

AndroidTtsControllerのキュー操作とコールバックを同じロックで直列化し、現在の発話IDだけを受け入れる。停止時に未初期化の保留文・待機キュー・発話IDを破棄する。古い再生状態通知も無効化する。

## 検証

ローカル全テスト: StandardDebug 1781件、StandardRelease 1244件、失敗0。追加10件では、完了時の末尾のみ読み上げ、重複完了、句読点なし短文、早期停止、再送信、古いコールバック、初期化前の停止を確認した。

実機: NX733J / SM8750、検証用パッケージio.github.ninbyo02.lami.gpucontrolledの通常チャット画面、NPU、TTS・ストリーミング読み上げON。ネイティブライブラリは前回の検証APKと全ハッシュ一致。通常利用パッケージにはインストールしていない。製品コードのビルド後変更は空白整形のみ。

| 操作 | 結果 |
|---|---|
| 挨拶 | 11文字、TTS要求・受理とも1回 |
| 長文 | 751文字、改行を除く743文字を計31回に分けてキュー投入。全文の二重投入なし |
| 長文の生成完了後に音声停止 | 停止前はCONTENT_TYPE_SPEECHのAudioTrackがstarted。停止2秒後・8秒後は再生中トラックなし、停止後のTTS要求・受理・開始なし |
| 短文 | 「赤」1文字、TTS要求・受理とも1回 |
| 生成・発話中に停止 | 86文字でCANCELLED。停止前は音声トラックstarted、停止2秒後・8秒後は再生中トラックなし、再開なし |
| 停止後の再送信 | 9文字で正常完了、TTS要求・受理とも1回 |

全正常完了はNPU。IMEと画面消灯時間を復元し、ChatGPTへ戻した。通常利用アプリの設定ファイルは前後で一致。

## 判定の範囲

端末内のTTSログとdumpsys audioで検証しており、人が聴いて判定した結果ではない。停止遅延の厳密なミリ秒測定は行っていない。検証スクリプトの初回は空のlogcatを参照して読み上げなしと誤判定したため、端末内ログと端末・PC時刻差を使って全シーケンスを再実行した。最初の試行を成功結果へ混ぜていない。

通常版GPUへのネイティブ統合、全バックエンドでの実機確認、長文の生成上限・回答品質は別課題。今回の長文も生成上限で文末が途中になっているため、長文生成能力全体の成功とは扱わない。
